# Chapter V diagram reproduction

Chapter V uses eight native Structurizr C4 component views and sixteen Mermaid
domain/data diagrams. These are **target design artifacts**, not evidence that the
reference backend already implements the modeled services.

## Sources and outputs

| Artifact | Source | Output |
|---|---|---|
| C4 component views | `docs/architecture/chapter-5/workspace.dsl` | `assets/chapter-5/{Identity,Supply,Discovery,Reservation,Payment,Notification,Agent,Audit}Components.svg` |
| C4 notation keys | Generated by the native Structurizr renderer | Matching `*Components-key.svg` files |
| Domain UML | `docs/architecture/chapter-5/<context>-domain.mmd` | `assets/chapter-5/<context>-domain.svg` |
| Database / Redis logical design | `docs/architecture/chapter-5/<context>-database.mmd` | `assets/chapter-5/<context>-database.svg` |

Context slugs are `identity`, `supply`, `discovery`, `reservation`, `payment`,
`notification`, `agent`, and `audit`. All report image paths are repository-relative.
Database diagrams are conceptual target schemas, not executable migrations.
Discovery's ER-shaped structures are Redis documents/indexes, not SQL tables or
foreign keys. Referential and concurrency constraints are explained in the report.

## Native Structurizr rendering

Verified toolchain: Java OpenJDK 24 and
`structurizr-2026.09.19-playwright.war` (Java 21 or newer required).
The Playwright-enabled WAR is available from the
[official binaries page](https://docs.structurizr.com/binaries).
Keep the downloaded binary outside the repository.

Run from the repository root, replacing `/path/to/` with its actual location:

```sh
java -jar /path/to/structurizr-2026.09.19-playwright.war validate \
  -workspace docs/architecture/chapter-5/workspace.dsl

java -jar /path/to/structurizr-2026.09.19-playwright.war export \
  -workspace docs/architecture/chapter-5/workspace.dsl \
  -format svg -output assets/chapter-5
```

The export uses Structurizr's browser-based renderer and automatic layout directly
from the DSL. It also emits a notation key per view. No Mermaid conversion is used
for C4. The first export downloads the required browser; Java validation alone does
not prove that images were rendered. Successful output must include all eight view
SVGs, with their component labels and relationships.

See [native SVG export](https://docs.structurizr.com/export/png-and-svg).

## Mermaid UML and data rendering

Verified CLI: `@mermaid-js/mermaid-cli` 11.14.0 with a working Chromium executable.
`docs/architecture/chapter-5/mermaid-config.json` retains the report's white-background
palette and disables HTML labels so SVG text does not depend on `foreignObject`
support in document viewers. If Puppeteer's default browser is unavailable, set
`PUPPETEER_EXECUTABLE_PATH` to the full path of a locally installed compatible
Chrome/Chromium executable; do not commit a machine-specific path.

```sh
for context in identity supply discovery reservation payment notification agent audit; do
  for kind in domain database; do
    mmdc -i "docs/architecture/chapter-5/$context-$kind.mmd" \
      -o "assets/chapter-5/$context-$kind.svg" \
      -b white -c docs/architecture/chapter-5/mermaid-config.json || exit 1
  done
done
```

Review the rendered SVGs for clipping, overlapping labels and legibility. Preserve
the eight Chapter IV context names, all required Chapter V subsections and the
separation between domain objects and storage schemas when editing.
